## 9. Instrument history (why some numbers changed)

Four defects were found in my own measurement code while building; each one moved a number, and none of them were in the model. Reported because the alternative is a quietly wrong result.

1. **Paired bootstrap sign inversion** — `paired_bootstrap_diff` computed `A−B` while documented as `B−A`, so `significant_win` fired when the *baseline* won. A `recall@5` row was labelled "YES" while Baseline A was actually the better system.
2. **Saturated abstention gate** — `no_answer_threshold=0.05` against RRF scores whose ceiling is ~0.033: abstention scored 1.000 on everything, and the product abstained on every question including answerable ones. Replaced with a content-overlap test (`engine/retrieve/relevance.py`).
3. **Mislabelled gold** — the stage evaluator took status from `_STATUS_MAP[e.kind]`, losing the `conditional` note the renderer itself records, so a correct reader scored `conditional` F1 = 0.00.
4. **Mismatched denominators** — the linker scored full-corpus predictions against holdout-only gold, reporting `supersedes` precision 0.221 when the true figure was 0.88; it also hid that only 13 of 171 edges disagreed with gold.

Two product defects the same audit caught, both silent in the code:

- **`G10` veto starved the flagship scenario.** Refusing to supersede any `status=mention` unit blocked the December→January update (a terse value statement has no status word), making System B score identically to Baseline A on the one case the project exists for. Removing it *raised* precision (0.917→0.944) and recall (0.64→0.68): the veto had been pure starvation, not protection.
- **Cross-project units inherited the meeting's project** instead of the discussed one, so a distractor about project B filed itself under A and the `G0` cross-project guard could never fire.
